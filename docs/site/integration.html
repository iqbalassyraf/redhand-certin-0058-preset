Integration

Everything a host application needs to consume the preset is machine-readable and versioned.

  • Discover it. redhand-shield manifest (or the redhand.presets entry point, redhand_fintech_shield.manifest:get_manifest) returns the preset id and version, the advisories it maps to, its policy fingerprint, and a catalog of every rule: stage, default severity, rationale, and whether it can be tuned or waived. docs/rules.md is generated from it and kept in sync by a test.
  • Validate against schemas. schemas/ holds JSON Schemas for the policy, findings, audit records, approval requests and claims, token claims, tool-call context and the manifest, each with a URN $id and a version. A change to any model is a visible diff, and redhand-shield schema --check fails when they are stale. The finding (M4.2) and mode (M4.3) shapes were written from the design specification, not from a RedHand release; diff them against RedHand's own schemas before wiring telemetry.
  • Know which policy decided. Every audit record and finding carries policy_sha256, a fingerprint of the rules in force (limits, rule overrides, exemptions; not file paths). redhand-shield fingerprint prints it, and verify-audit --expect-policy HASH fails unless every record was decided under that policy. The preset's own content is pinned by preset_version plus a golden fingerprint, so it cannot change silently.
  • Tokens: audience, rotation, revocation.

```yaml audience: payments-gateway # tokens must carry this aud (AgentTokenIssuer.mint(audience=...)) token_keys: # rotate without an outage

  • {kid: 2026-q4-a, public_key_path: keys/a.pem, retire_at: 2026-12-31T00:00:00Z}
  • {kid: 2026-q4-b, public_key_path: keys/b.pem} revocation_journal_path: revoked.jsonl ```

Sign with AgentTokenIssuer(key, kid="2026-q4-b"); a token must name a known kid, and a key stops verifying at its retire_at. redhand-shield keygen keys --kid 2026-q4-b prints the token_keys entry. To stop a leaked token, redhand-shield revoke revoked.jsonl --run RUN --reason "..." (or --jti, --subject); a running shield picks it up within a second. There is deliberately no jti replay cache: a run token is presented on every call of its run, so rejecting a second use would break normal operation. Revocation is the control for a stolen token.

  • Plug in shared state. Shield(..., audit=, quarantine=, nonce_store=, revocations=, window_store=, telemetry_sink=) accept your own backends; each is a narrow typing.Protocol in redhand_fintech_shield.protocols. Run redhand_fintech_shield.testing.window_store_contract(factory) in your tests to check a window store. Sharing detector state has limits: the shield's lock makes check-then-record atomic only inside one process, so across workers a cumulative cap can overshoot by up to the number of concurrent workers, and workers sharing a store need a shared time base (pass a wall-clock monotonic= to the shield).
  • Depend on a stable API. docs/public_api.json snapshots every name in redhand_fintech_shield.__all__ with its signature; a test fails on any difference. Breaking changes and deprecations follow the policy in CONTRIBUTING.md.
